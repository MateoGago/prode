## Compact Rules

### vercel-react-best-practices
- Server Components by default; add `"use client"` only when interactivity requires it.
- Fetch on the server, colocate data fetching, avoid client request waterfalls.
- Memoize only with measured need; avoid premature `useMemo`/`useCallback`.
- Keep client bundles lean; dynamic-import heavy client-only pieces.
- This is Next 16 — verify every API against `node_modules/next/dist/docs/` before use (breaking changes vs training data).

### vercel-composition-patterns
- Replace boolean-prop proliferation with composition (children, slots, compound components).
- Prefer compound components / context over deeply-threaded props.
- React 19: use new APIs (`use()`, Actions, ref-as-prop) where they simplify.

### clean-code
- Intention-revealing names; small functions doing one thing.
- No duplication; comments explain WHY, not WHAT.
- Keep business logic (scoring rules, lock rules) pure — no framework/infra imports. Screaming: organize by feature, separate pure logic from infra/ui within each feature.

### tdd
- Red → Green → Refactor. Write the failing test first.
- Scoring engine and prediction-lock rules are pure domain → ideal for unit TDD.
- BLOCKED until a test runner is installed (see testing-capabilities). Add Vitest first.

### cybersecurity-analyst
- Anti-cheat enforced server-side (Postgres RLS / SECURITY DEFINER trigger), never trust the client clock.
- Compare absolute time (`now()` UTC vs `kickoff_at` UTC). Reject prediction INSERT/UPDATE when `now() >= kickoff_at`.
- Least-privilege RLS: a user reads/writes only their own predictions; matches/results are read-only to players.

### git workflow (branch-pr, work-unit-commits, chained-pr, issue-creation, comment-writer)
- Conventional commits, NO AI attribution (user rule).
- Plan commits as reviewable work units; keep tests + docs with the code they cover.
- PRs > 400 lines → split into chained PRs.
